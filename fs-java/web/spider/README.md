# 数据采集

## 架构设计

### 采集角色

- 服务端（Spider）：用于配置和分发作业，负责任务调度、状态存储、采集结果数据存储。
- 采集端（Crawler）：从服务端获取任务，执行完成后将结果提交回服务端，若响应类型为文件，则转存到文件存储。
- 浏览器端（Browser）：使用 Playwright 执行动态页面，将渲染后的 HTML 返回给采集端。
- 助手端（Assist）：辅助页面进行拦截验证。
- 识别端（AI）：图片识别、手势识别等。

### 协作角色

- 清洗端（ETL）：将采集的原始数据，按照一定的规则处理为高质量的业务数据，同时将正文中的图片转存到图床。
> 清洗算法：页面类型判定（首页、列表页、详情页等）、新渠道发现、列表首页标记、详情提取。

### 原则

- 全量采集：只要在白名单中的站点，尽可能高效全面的采集下来。
- 增量采集：根据清洗端标记的列表首页，定期进行回溯，根据列表项重复率确定是否进行翻页。
- 存储方式：服务端负责将采集结果存储到Mongo集合，采集端在请求链接时负责将文件转存到S3对象存储桶，清洗端负责将正文中的图片写入到图床。

### 智能采集

- 页面类型由静态 HTML DOM 判定，`type` 取值为 `list`（列表）、`detail`（详情）或 `other`（其他）。
- 每次采集会按目标 Mongo 集合比对当前页面链接。发现新链接后，将新链接和本次页面中已判定为 `list` 的旧链接以强制重采方式入队。
- `crawl_times` 累计页面采集次数，`new_link_times` 累计该页面发现新链接的次数，两项均使用 MongoDB `$inc` 原子更新。

### 实体

- 作业：为避免资源浪费，每个模板仅保留一个调度作业。通过发布操作将模板配置同步到作业，通过运行操作执行作业调度，多次执行操作共享同一个调度队列。
- 请求频率：全局共享，防止多个作业请求同一域名，导致请求数过多。可以通过设置每作业、每域名、每节点、每代理，控制请求数的共享范围。

### 配置

- 作业最大线程数：限制作业可申请的最大资源数量。
- 请求频率并行度：按共享范围，限制同时在执行的请求数量。
- 请求频率并发数：按共享范围，限制特定间隔内已发出请求的数量。
- 页面请求策略：泛采集、单页采集和智能采集按渠道站点配置 `http` 或 `browser`，
  以及页面就绪条件、等待元素和超时；定向采集按流程页面配置。模板不再保存请求模式。
  浏览器模式按 ZooKeeper `/runtime/browsers` 中上报的实时负载选择节点。
- 浏览器资源不足：采集端不等待和重试，立即把任务作为可重试错误上报，由 Spider
  将任务放回 Redis 队列。是否继续调度由 Token、优先级和模板停顿参数共同控制。

### 无头浏览器节点

```bash
gradle :web:browser:installPlaywright
gradle :web:browser:bootJar
```

浏览器服务的 ZooKeeper 命名空间必须与 Spider/Crawler 一致。服务默认监听 `7836` 端口，
通过 `web/browser` 的 `application.yml` 调整并发数、超时、资源拦截和启动参数。
